# Experience First

When an easy implementation conflicts with a good user experience, choose the good experience.

- Each feature, control, and option must have a reason to exist.
- Ship less, but ship it better. A polished experience with three features is better than a rough one with ten.
- Prototype before you commit. A design decision costs less in throwaway code than in production code.
- Get the details right: transitions, alignment, spacing, feedback, and error states.
- Keep the core workflow tight. Each feature must serve the main workflow or stay out of its way.

The user is whoever uses the work. For a UI, it is the end user. For a library or an internal API, it is the colleague who imports it. The next engineer who maintains the code is also a user. Weigh their experience the same way, and explain the impact from their point of view.

Foundational thinking controls the order of the work. This principle controls the goal.
